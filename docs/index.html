How it works

Open. Inspect. Hand off.

Files are parsed in this browser using the C parser compiled to WebAssembly. CRC checks detect some transmission damage; they do not authenticate a sender or verify signed-frame signatures.

Unknown message IDs are reported as unsupported, not automatically corrupt. Sequence gaps are estimates under a single fully observed channel and in-order arrival assumption.

Contextual observations

    Heuristics flag changes for review. They do not confirm an attack or command execution.

    Methods and limits

    Only CRC-accepted frames feed these observations. GPS review threshold: over 100 m/s between 3D fixes. Relative-altitude review threshold: over 20 m/s. Comparisons require the same system, component and message type, with increasing capture timestamps no more than five seconds apart. Timestamp reversals disable rate checks. Capture times are not trusted flight times. Vehicle capability, sensor accuracy, authorization and flight context require separate evidence. CRC validates transmission integrity, not sender identity. At most 10,000 retained frames, 12 telemetry readings and 100 observations are shown.

      Format help

      What you can open

      A .tlog file (each record is an 8-byte big-endian microsecond timestamp followed by one frame, as written by ground stations) or a raw byte stream containing MAVLink v1, v2 or both. Auto-detect picks .tlog from the file name or a plausible initial timestamp. Captures up to 256 MiB are read in this tab; the first 4,000,000 frame details, 100,000 issue details and 100,000 sequence events are retained. Totals cover the whole file. Message/sender grouping is capped at 10,000 combinations and reports disclose truncation.

      MAVLink v2 frame layout

      Bytes of one MAVLink v2 frame
      BytesFieldNotes
      0Start byte0xFD for v2. V1 uses 0xFE and is parsed using its own six-byte header.
      1Payload length0 to 255. Trailing zero bytes of the payload may be trimmed by the sender.
      2Incompat flagsOnly bit 0 (signed) is supported; any other bit makes the frame a "bad flags" reject.
      3Compat flagsIgnored.
      4Sequence8 bits per sender, wraps at 255.
      5–6System ID, component IDShown as sys:comp.
      7–9Message ID24 bits, little-endian.
      10…Payload326 pinned common/ArduPilot message definitions, including arrays, enums and v2 extensions. Reconstructed zero tails are labelled separately from wire bytes.
      +2CRCCRC-16/MCRF4XX over bytes 1 to the end of the payload plus the message's CRC_EXTRA byte.
      +13SignatureOnly when signed: link id, timestamp, hash.

      V1 layout: start byte, payload length, sequence, system ID, component ID and one-byte message ID, followed by payload and two-byte CRC. V1 has no incompat/compat flags, extension fields or signature trailer. Both CRC calculations run in the native C engine.

      Live radio

      Reads USB serial bytes through the C/Wasm parser; it sends no commands and uploads nothing. Arrival rate is measured per browser read, not per packet. Inspection retains only the last 8 MiB; counters cover the full session up to 1 GiB or 30 minutes. Earlier bytes are discarded. A clean disconnect keeps the tail until a new session or page close; parser failure can make it unavailable. Sequence gaps are estimates and CRC candidates may include resynchronization noise. Unchecked custom-dialect headers can advance sequence estimates without becoming verified frames. Physical-radio validation is unrecorded.

      Fuzz

      Runs 1,000 deterministic valid, bit-flipped, truncated, empty and random-noise inputs through the compiled C parser in a worker. The loaded capture remains unchanged. Seed: 0x5eed1234.

      CRC failed, unsupported, bad flags

      CRC failed: the header looked valid, but the checksum the parser computed does not match the two CRC bytes in the capture. The frame is discarded and the parser looks for the next start byte inside it, so a valid frame hidden in damaged bytes is still found. Frame details shows the wire and computed values side by side.

      Unsupported: the message id is outside the pinned common/ArduPilot definitions, so its CRC_EXTRA is unknown and the checksum cannot be checked. It may be a custom dialect or noise. These are never counted as corrupt. Full native candidate counters remain in capture reports; the .tlog presentation separately classifies timestamp artifacts and nested candidates.

      Bad flags: incompat flags other than "signed", which this parser does not support.

      Sequence gaps and the channel assumption

      For each sender, sequence steps are classified as in order (1), duplicate (0), gap (2 to 128: about step − 1 frames missing) or step back (late when small, otherwise likely sender restart). A gap is an estimate, not measured RF loss. It assumes one fully observed channel per sender and in-order arrival; a late frame, filtered route or merged links can look like loss. See MAVLink packet-loss assumptions (opens in a new tab).

      Signatures

      Signed frames carry 13 extra bytes. The inspector shows them as "signature present; not verified": checking a signature needs the link's secret key, and the parser does not do it.

      The bundled sample

      The sample (sample/sample-flight.tlog) is synthetic, not a real flight. tools/gen_sample_tlog.py generates known CRC failures, sequence gaps and skipped bytes for exact-count tests; these values say nothing about a vehicle.

      Finding export

      Frame details can save one row as JSON: tool version, file name, size and SHA-256, offsets, CRC wire vs computed, the sequence note if any, and the assumptions above. All payload bytes are left out by default. The checkbox adds them when a full frame was retained; raw bytes may contain GPS/position or other sensitive data. Unsupported and bad-flags candidates retain only a header, so their payload and CRC are unavailable.

Coverage is measured against the pinned common + ArduPilotMega XML graph only; other dialects and hardware behavior are not claimed. See the machine-readable message/field coverage inventory.
